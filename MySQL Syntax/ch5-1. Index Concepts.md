# Chapter 5-1 — Index Concepts

> What an index is and the two kinds MySQL uses.

## 1. What an index is

An index is an extra, sorted lookup structure that lets the DBMS jump straight to rows instead of scanning the whole table — exactly like the index at the back of a book versus reading every page.

- **Without an index:** *full table scan* — read every row.
- **With an index:** *index search* — go almost directly to the matching rows.

**Trade-off:** indexes speed up `SELECT`/`WHERE`/`JOIN`/`ORDER BY`, but cost extra disk space and slow down `INSERT`/`UPDATE`/`DELETE` (the index must be kept in sync).

## 2. Two types of index

| Type | Created by | Key property |
| --- | --- | --- |
| **Clustered index** | `PRIMARY KEY` (or first `UNIQUE NOT NULL`) | The **table rows themselves are physically sorted** by this key. **One per table.** |
| **Secondary index** | `UNIQUE` / `CREATE INDEX` | A **separate** sorted structure that points back to the rows. **Many allowed.** |

### Analogy

- A **clustered index** is like a dictionary: the entries *are* the data, stored in sorted order — there is only one such order.
- A **secondary index** is like a textbook's back-of-book index: a separate list of terms with page pointers — you can have several (by term, by author, etc.).

## 3. Practical implications

- A table with a clustered index keeps its data sorted by the PK, so PK-range queries are very fast.
- Choosing the PK effectively chooses the table's physical sort order — pick it deliberately.
- Secondary indexes add flexibility but each one adds write cost.

## Key takeaways

- Index = faster reads, slower writes + more storage.
- **Clustered** = data sorted in place, one per table (usually the PK).
- **Secondary** = separate structure with row pointers, many per table.
