# Chapter 6-1 — Stored Procedures

> A named, reusable block of SQL stored in the database.

## 1. Concept

A **stored procedure** packages one or more SQL statements (plus programming logic) under a name. You define it once and run it with `CALL`.

## 2. Defining and calling

`DELIMITER` temporarily changes the statement terminator so the semicolons *inside* the procedure aren't treated as the end.

```sql
DELIMITER //
CREATE PROCEDURE my_proc()
BEGIN
    SELECT * FROM member WHERE mem_number >= 6;
END //
DELIMITER ;

CALL my_proc();      -- run it
DROP PROCEDURE my_proc;
```

## 3. Parameters

| Mode | Direction |
| --- | --- |
| `IN` | input (default) — caller → procedure |
| `OUT` | output — procedure → caller |
| `INOUT` | both |

```sql
DELIMITER //
CREATE PROCEDURE proc_param(IN in_height INT, OUT out_count INT)
BEGIN
    SELECT COUNT(*) INTO out_count
    FROM member WHERE height >= in_height;
END //
DELIMITER ;

CALL proc_param(165, @cnt);
SELECT @cnt;
```

## 4. Why use stored procedures

- **Performance / network** — one `CALL` replaces many client round-trips.
- **Modularity & reuse** — logic lives in one place.
- **Security** — grant `EXECUTE` on the procedure without granting direct table access.
- **Maintainability** — change the logic centrally, not in every app.

## 5. Inspecting

```sql
SHOW PROCEDURE STATUS WHERE Db = 'market_db';
SHOW CREATE PROCEDURE my_proc;
```

## Key takeaways

- A stored procedure = stored SQL logic, run by `CALL`.
- Use `DELIMITER` around the body so inner `;` aren't misread.
- Parameters come in `IN` / `OUT` / `INOUT` modes.
- Benefits: fewer round-trips, reuse, and access control via `EXECUTE` grants.
