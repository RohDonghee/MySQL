# Chapter 6-3 — Triggers

> Code that fires automatically when a table is changed.

## 1. Concept

A **trigger** is attached to a table and runs **automatically** in response to an `INSERT`, `UPDATE`, or `DELETE` — the caller never invokes it directly. Typical uses: audit logging, backups of changed rows, and enforcing complex rules.

## 2. Timing and event

```sql
CREATE TRIGGER trigger_name
    { BEFORE | AFTER } { INSERT | UPDATE | DELETE }
    ON table_name
    FOR EACH ROW
BEGIN
    -- trigger body
END
```

- **`BEFORE`** — runs before the change (can validate/modify the incoming value).
- **`AFTER`** — runs after the change (good for logging what happened).
- `FOR EACH ROW` — the body runs once per affected row.

## 3. `NEW` and `OLD` pseudo-tables

Inside a trigger you access the row being changed:

| Event | `OLD` (before) | `NEW` (after) |
| --- | --- | --- |
| `INSERT` | — | the inserted row |
| `UPDATE` | the old values | the new values |
| `DELETE` | the deleted row | — |

## 4. Example — back up deleted rows

```sql
CREATE TABLE member_deleted (
    mem_id   CHAR(8),
    mem_name VARCHAR(10),
    deleted_at DATETIME
);

DELIMITER //
CREATE TRIGGER trg_member_delete
    AFTER DELETE
    ON member
    FOR EACH ROW
BEGIN
    INSERT INTO member_deleted
    VALUES (OLD.mem_id, OLD.mem_name, NOW());   -- archive the removed row
END //
DELIMITER ;
```

Now any `DELETE FROM member …` automatically archives the removed rows into `member_deleted`.

## 5. Managing triggers

```sql
SHOW TRIGGERS FROM market_db;
DROP TRIGGER trg_member_delete;
```

## Key takeaways

- Triggers run automatically on `INSERT`/`UPDATE`/`DELETE`; choose `BEFORE` or `AFTER` timing.
- `NEW` holds incoming values, `OLD` holds previous values (availability depends on the event).
- Classic use cases: auditing, archiving deleted rows, and enforcing rules that constraints can't.
- Because they fire invisibly, document them — they can surprise people debugging "why did this row appear?"
